## 3. 关键设计点：损坏文件不变成空房间

GLM 特别指出这点「工作单没明说」。我重点验了。

场景：把房间文件写成垃圾 `THIS IS NOT JSON {{{`，然后重启。

| 检查 | 结果 |
|---|---|
| 服务照常启动 | ✅ |
| 日志报出损坏文件 | ✅ `[repository] skipping corrupt room file ...` |
| 该房间返回 **404**（缺席） | ✅ |
| **不是空房间** | ✅ |
| 损坏文件**仍在磁盘** | ✅ |
| 文件内容**未被覆盖** | ✅ |

**为什么这个设计是对的**：

如果 `list()` 也把损坏房间列出来，`restoreAll()` 就会 `create()` 一个空房间，
而这个空房间一旦 `save()`，**就把损坏文件覆盖了**——证据销毁，再也查不出问题。

现在的行为是「房间缺席、文件保留」，符合「失败要可诊断」的原则。

GLM 主动想到并测了这点，比工作单要求更严。

## 5. 一个观察（不阻塞）

`save()` 是同步的，每落一子写一次文件。GLM 在注释里写明了取舍：

> Synchronous on purpose: a move must be durable before the response goes
> out, and at 9x9 the write is a few milliseconds. Revisit if boards grow or
> writes become high-frequency.

**这个判断是对的**：

- 9 路最多 81 手，一子一写完全没问题
- 同步保证「响应发出前已落盘」，不会丢数据
- 注释留了升级路径

如果以后做 19 路围棋或高频聊天室，需要考虑批量/异步。记入待办。

## 6. 一个必须提醒用户的事

GLM 在说明里提到：

> 你 3000 端口上还跑着旧代码的 dev server，下次重启它就获得持久化——
> 届时旧内存房间无法找回（那盘棋已随旧进程消失，这正是本份要修的问题）。

**这是对的，而且要说清楚**：

- 那盘已经下完的棋**确实找不回来了**（内存里的，进程没了就没了）
- 但**从下次重启开始**，所有新对局都会落盘

我已在合入后重启服务（用新构建），从现在起对局会持久化。
