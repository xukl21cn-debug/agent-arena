# 评审怎么做

评审前先读本页。工作量与独立评审的适用场景见[开发工作流](workflow.md)，角色见 [AGENTS.md](../AGENTS.md#分工)。

---

## 1. 独立验证的套路

**不要只看实现者的测试。** 无论由哪个 harness / 模型实现，自测通过都不等于独立验收通过。工作 agent 可以协助检查和复现，统筹 agent 负责复核证据并给出评审结论；若统筹参与了实现，标明自验身份。需要独立评审时，把已确认场景、基线、diff 和运行证据交给未参与实现的评审者，由统筹汇总。

```text
1. 从规则/需求出发，自己写检查（不照搬实现者的断言）
2. 用真实服务，不用 mock
3. 覆盖边界：空值、越界、类型错、拼写错
4. 验证**行为**，不只是返回值
5. 检查「拒绝后不留残留」
```

复杂重构的评审者将每轮结论写入同一份 Proposal 或架构文档的审核小节；日常小任务由承接者自测、用户验收。独立评审记录应写明实现者与评审者的实际 harness / 模型、提交基线、独立检查结果及未覆盖项。不要将工作 agent 的回报直接标记为统筹 agent 已独立验证。

## 2. 踩过的坑（评审方自己犯的，别再犯）

| 坑 | 教训 |
|---|---|
| **复用房间名** | 上次运行的参与者还在，`AMBIGUOUS_ACTOR` 让后续全部失败。**每次用带时间戳的新房间名** |
| **`timeoutMs` 传太小** | schema 下限是 1000，传 800 直接报错。**调工具前确认参数范围** |
| **测试双人系统时只放一个人** | 没有对手方，轮次永远不推进。**必须两个会话都在场** |
| **断言字段名猜错** | `komi` 在 `state.rules.komi` 不在顶层；`get_transcript` 返回 `messages` 不是 `transcript`。**先 dump 一次真实响应** |
| **选择器选错元素** | 用 `circle` 数棋子，但棋子是 `span.stone`，`circle` 是**星位**、恒为 5 个——于是「开局 0 子」也报 5。排除空位上的预览子，使用 `span.stone:not(.stone--preview)`，同时核对页面局面 |
| **算术写错期望值** | 断言「后退一帧后 7 颗子」，但第 7 手加一子同时提一子，总数不变。**涉及棋子的加减先手算一遍再写** |

**这几条已经犯了不止一次。写审计脚本前先对照一遍。**

## 3. 实测脚本怎么写

- 用真实 MCP 客户端（`@modelcontextprotocol/sdk`）
- 浏览器用 CDP 直接驱动 Chromium（`--remote-debugging-port`），不需要 playwright 包
- 一次性检查脚本放临时目录。需要长期防止同一回归时，将行为断言放入相应测试。
- 文档改动用正常入口验证能否找到答案，再检查相对链接、命令、源码路径和历史证据引用。UI 改动实走浏览器，模型行为改动实走客户端；回报中注明用户尚未体验的部分。
