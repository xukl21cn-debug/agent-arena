# 开发工作流

开工时只判断一件事：这次改动能否在既有边界内，用一个明确的使用场景验收？能，就由一个 agent 做完；涉及领域职责、公共契约、旧数据或尚未定下的架构取舍，就走重构流程。按影响判断，即使只改一行，改变旧客户端行为也要走重构流程。[项目分工](../AGENTS.md#分工)

## 日常小任务

1. **一个 agent 接到底。** 复现现象，用原请求或一句话确定预期，直接改代码。小任务免设计稿、免派单、免独立审核。
2. **从实际入口验证。** 运行相关单测；修 bug 时覆盖原先失败的场景。涉及界面再实际触发一次，纯文档改动检查链接和示例。把改动、结果和最短复验步骤回给用户即可。
3. **人工验收后合入。** 用户体验或核对结果，明确放行后，由同一 agent 合入并跑全量测试。用户尚未验收时，状态写“待验收”。

例如修正大厅慢响应下的加载提示，可以直接模拟慢请求并观察页面。若排查发现必须改变大厅与房间的公共响应格式，在改契约前把影响带回用户，转入下轨。

## 复杂架构重构

**一项重构只有一份主文档。** 新议题使用 `docs/proposals/<主题>.md`；若已有架构文档负责这个主题，可直接在其中提出变更，并标清“拟议”与“已生效”。以下四步写在同一份文件里，用 Git 保留各版。返工沿用原文件和原任务。

| 步骤 | 谁做什么 | 何时进入下一步 |
|---|---|---|
| 1. 需求确认 | 统筹写实际场景、当前与期望行为、范围和可观察的验收条件。 | 用户确认理解；影响产品行为的分歧已有决定。 |
| 2. 方案设计 | 在同一文档说明涉及的模块、拟修改的边界、兼容或迁移方式和验证方法。用一个完整场景说明方案为什么可行。 | 技术边界明确；新增的产品或兼容取舍已经用户确认。 |
| 3. 实现 | 实现者按已确认方案完成一个可体验的切片，在原文档记录提交、测试和遗留项。发现前提失效就回到对应步骤。 | 有可复验的结果和明确的实现基线。 |
| 4. 独立审核 | 未参与实现的人或 agent 从验收场景和 diff 出发独立验证，把结论、证据、未覆盖项写回原文档。 | 未通过则退回实现；通过后由用户最终验收、放行合并，合入后跑全量测试。推送单独授权。 |

例如调整“谁能放行合并”，在编码前先说清执行者尚未收工时，用户会在看板看到什么。审核者用独立会话走一次过早放行和一次正常放行，检查任务状态、唤醒和最终证据。[评审方法](reviewing.md)

## 文档和交接

- 小任务的结果留在对话或已有 PR。重构的需求、取舍、实现回报和逐轮审核都写进同一主文档。多个客户端通过 `/work/mcp` 交接时，由看板传递任务与轮次，附件引用主文档的版本。[工作看板](dev-workflow.md#工作看板)
- 合入后，只把持续有效的边界、约束或使用方式更新到对应的长期文档。直接在架构文档上开展的设计，收尾时把正文整理为已生效的结论，过程可从 Git 回查。
- 按主题维护主文档，停止按阶段建目录或按角色拆文件。
