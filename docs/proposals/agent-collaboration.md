# 通过 MCP 交接开发任务

> 设计提案 · 2026-11-17。接口名与分期均为拟议方案。现行分工见 [AGENTS.md](../../AGENTS.md) §2–3。
> 已接入聊天室的客户端可先按名字直接派单和等待回报，见[现行试跑步骤](../dev-workflow.md#61-用聊天室交接开发任务)。下文的 runner 用于接续已经结束的轮次。

## 1. 从聊天室 runner 到开发任务交接

Runner 已经写在 2026-10-24 的聊天室原提案里，编号 P4-C3。原设计让常驻进程等待聊天轮次，调用一个 CLI，把回复发回房间。当前已实现聊天长轮询、点名轮转和保存转录，P4-C3 仍是路线图中的待选项。MCP 支持服务端通知，但能否把一条通知变成某个桌面会话的新一轮工作，由客户端提供的能力决定。[聊天室原提案 §5](agent-chat.md#5-唤醒长轮询--runner) · [路线图 §11.2](../roadmap.md#112-runner-的原始设想) · [MCP 传输规范](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

开发协作可以沿用 runner 的「等待 → 执行 → 回报」，并补齐三个环节。

| 环节 | 职责 |
|---|---|
| Arena 的任务与事件 | 保存工作单、目标会话、工作回报、复审意见和合并结果。断线期间也能排队，重新连接后可追踪。 |
| 本地 runner 与客户端适配器 | 从 MCP 领取交接，确认目标和工作目录，把任务送进指定会话的一轮输入，采集最终输出和执行结果。 |
| 统筹与工作 agent | 统筹决定任务拆分、承接人、复审与合并。工作 agent 按任务范围实现、自测和回报。 |

协作状态独立于聊天轮次。聊天默认发言租约为 120 秒，单条消息默认限长 4000 字符，适合短消息。开发任务需要持续到编译、测试和评审完成，完整工作单与回报作为任务记录存储。房间时间线显示状态和摘要，按引用查看原文。[聊天室默认策略](../../server/src/chat/model.ts)

## 2. 把现在手动转贴的流程跑通

| 现在手动做的事 | 接入后的行为 |
|---|---|
| 在 Codex 里说明需求，由统筹写工作单 | Codex 保持现行 `handoff.md` 流程，通过 MCP 派单时关联工作单版本、基线、目标分支、验收项和回报对象。用户可以指定 AGY、ZCode 或 DSH 的具体会话。 |
| 把工作单复制进工作 agent 的窗口 | 目标会话从自己的待办领取任务。若上一轮已结束，runner 用该客户端的接口打开下一轮，保留已绑定的会话上下文。 |
| 把修复总结、提交和测试结果粘回 Codex | 工作端回报完整最终回复及结构化证据。Arena 保存结果后向**原 Codex 会话**排入复审；会话空闲时启动复审，忙时保留待办。 |
| 把复审意见转贴回去，等它再改一轮 | Codex 记录缺陷、复现条件和验收项，提交返工决定。Arena 创建同任务的新一轮交接，明确返工基线。新回报继续返回原 Codex 会话。 |
| 复审通过后验收，按授权合入 main | 通过及合并分别记录，确认被评审的提交与合入候选一致。已有合并授权可随任务记录，需要用户验收时在网页或原会话完成。合并提交与合并后测试结果回到同一任务。 |

例如，Codex 派 AGY 整改 R3/R4。AGY 回报提交与测试结果后，Codex 独立复现慢响应，发现 R4 仍有问题，记录返工依据并送回同一 AGY 会话。下一次提交通过独立验证后再进入验收或合并。首次指派后，用户只需要在要改变方向或作出验收决定时介入。

## 3. 会话绑定与适配

- **绑定到会话。** 绑定记录包含项目、主机或客户端实例、harness、该客户端的会话 ID、工作目录和可执行动作。显示名用于选人，实际投递用稳定的绑定 ID。同一项目中两个都叫「Codex」的会话有各自的收件箱。新建工作会话和接入现有会话由用户明确选择；派单时固化回报目标。
- **支持两种收件方式。** 正在工作的会话可以挂起一个 MCP 调用等交接。空闲会话由 runner 调用适配器开启下一轮。一个绑定同一时刻只允许一种方式领取本次交接；有正在运行的那一轮，就让后续任务排队。
- **将连接与会话分开。** MCP transport session ID 可以变，任务和客户端会话绑定持久保存。重新握手后凭绑定凭据恢复，显示名和客户端自报名称只用于展示。会话不存在、换了目录、已有活动轮次或需要客户端审批时，待办保留，并给出明确状态。
- **约定输入输出。** 下一轮输入包含任务号、工作单原文、验收标准、分支、基线、上轮回报和复审意见中需要继续的部分。工作端保留用户可见的最终回复，并单独回报提交哈希、变更文件、自测命令和结果、未解决项。首次复审所需的提交与测试证据随引用可读。采集范围为交接内容和明确选择的证据，客户端完整历史由各自客户端管理。

| 客户端 | 可用入口 | 接入时要实测 |
|---|---|---|
| Codex | CLI 支持 `codex exec resume <session-id>`，App Server 有 `thread/resume` 和 `turn/start`。 | 优先验证用户指定的桌面会话在空闲后能接到下一轮，结果在原会话中可见。能续接 CLI 会话与能操作当前桌面实例是两个验收项。[CLI 文档](https://learn.chatgpt.com/docs/non-interactive-mode#resume-a-non-interactive-session) · [App Server 文档](https://learn.chatgpt.com/docs/app-server) |
| DSH | 本机 `dsh headless --help` 列出 `--session-id`、stdin 和 JSON 事件输出。 | 按已知 ID 连续跑两轮，获取同一会话 ID 和最终回复，确认工作目录和权限。另测已打开的 Web/TUI 会话能否接入。 |
| AGY | 本机 `agy --help` 列出 `--print`、`--conversation` 和 JSON 输出。 | 验证已安装版本能否按指定 conversation 续跑并返回完整最终回复，以及现有交互会话的可见性。 |
| ZCode | 官方 CLI 文档列出非交互执行及 `sessionId`、`response` 输出。 | 在本机实际安装版本验证 CLI 入口、精确续接、权限与已开桌面会话联动。[ZCode CLI 文档](https://github.com/zai-org/ZCode/blob/main/apps/zcode-cli/docs/usage/01-quickstart.md#第一次非交互调用) |

适配器使用本地配置的可执行文件、参数模板和工作目录。MCP 工作单正文作为提示数据传入，客户端权限沿用该绑定选定的模式。Arena 记录实际 harness / 模型和外部轮次标识，供复审追溯。

## 4. MCP、任务状态与可靠投递

拟在同一个 Arena 服务加入口 `arena-work`（`/work/mcp`），协作 room 按项目组织任务，网页沿用现有大厅和事件推送方式。工作工具和身份权限集中在该入口，按需接入。用户在网页打开一个任务时可以查看完整上下文、当前承接会话、工作目录、进度和操作历史，也可补充说明、重新指派或接管。

| 操作 | 拟议 MCP 工具与返回 |
|---|---|
| 派单与查询 | `create_task` 接收项目、目标绑定、回报绑定、任务范围、工作单引用和基线，返回 `taskId`。`get_task` 读取状态、回报和时间线。 |
| 收件与恢复 | `wait_for_work` 按当前绑定和游标返回可领取交接，断线后继续查询。 `claim_delivery` 原子领取，返回 `deliveryId` 和租约；长任务以 `update_delivery` 记录带外部轮次 ID 的启动回执并续租。 |
| 执行回报与复审 | `submit_result` 收工作 agent 的报告并排入复审。 `record_review` 登记复审结论及证据，退回时生成下一轮执行交接。 `update_delivery` 可登记客户端错误、取消和人工接管等投递结果。 |
| 验收与收尾 | `decide_task` 记录用户验收、需要调整或取消。已经具备合并权限时，Arena 向原统筹会话排入收尾交接。 `record_merge` 关联已评审的候选提交，分别记录合并提交与合并后验证结果。 |

主流程为 `待领取 → 执行中 → 待复审 → 复审中 → 待验收或可合并 → 合并后验证 → 完成`。复审未通过回到待领取，新增工作单修订和交接记录。客户端离线、忙碌、待审批及投递状态不明作为交接状态显示，不抹掉任务当前阶段。执行失败可保留部分回报，用户或统筹可从已知工作区继续。

- **任务、交接、轮次有各自的标识。** 一个任务可经历多次执行、复审和返工。每次交接绑定任务修订、目标会话和角色，领取后才可以回报。旧租约或旧修订的迟到结果保留诊断记录，当前进度保持由对应的有效交接推进。
- **任务变更与下一份待办一起落盘。** 提交结果、生成复审交接、写入事件在同一持久化事务内完成。复审通过且已有授权，或用户事后验收时，同样原子地创建收尾交接。派单和回报请求带幂等键，重发同一请求返回原记录。游标用于读取新增事件，仍可领取的待办一直可查。存储按本地单服务设计，具体后端在实现工作单里选型，并保留项目现有 Node 版本约束。
- **重试按是否已启动区分。** 未领取或可证实尚未启动的交接可以重新排队。客户端可能已经开始修改文件时，使用外部轮次 ID 或可核对的运行记录对账；无法确认时将交接标为「待接管」，继续展示已有结果。服务重启先恢复待办，runner 重新绑定后再领取。发送成功但回执丢失需要覆盖，避免重试带来第二轮修改。
- **同一工作区的写入串行。** 工作单记录仓库、分支、基线提交和分配的 worktree。runner 执行前核对，活跃写任务独占该 worktree，续租失败后确认原执行已结束才重新分配。独立任务用独立 worktree 并行，合并在同一仓库串行。主线基线改变或被评审的候选提交改变时，统筹重新同步和验证后再合并。合并已执行但后续测试失败时保留实际合并状态，标记待处理。
- **投递成功和技术验收各自记录。** runner 报告客户端是否已接收、是否产出结果。统筹通过独立检查给出技术结论。已有合并授权绑定到仓库、目标分支与具体任务范围，需要时再由用户验收。合并操作按项目工作流执行，保留结果与命令证据。

## 5. 分期与验收

| 分期 | 交付范围 | 通过条件 |
|---|---|---|
| 1. 同会话闭环 | 一个项目、一个统筹会话、一个 DSH 工作会话、持久交接。优先实现 Codex 结果回投。 | 用户在指定的 Codex 会话只发一次指令。DSH 在其分配工作区执行，完整回报自动进入**同 ID 的原 Codex 会话**并启动复审。让 Codex 在派单后结束当前轮次，验证空闲时仍能收到结果。 |
| 2. 跑完现有开发流程 | 返工、复审、用户验收与合并结果、网页任务时间线。 | 首次复审发现一个可复现问题并自动返工，同一工作会话收到反馈并回报第二个提交。用户能查看两次回报，指定验收决定，并核对合并前后证据。只有用户决定或明确设定的其他执行授权需要人工输入。 |
| 3. 多客户端与并行 | 接入 AGY、ZCode，按实测支持已有会话或托管会话。 | 两个同名会话精确路由。两个工作 agent 各用独立 worktree，结果回到正确的发起会话。每个支持的客户端分别通过启动、续接、失败及审批验证。 |

第一阶段的阻塞点是目标桌面会话能否被精确续接。先用测试会话验证原会话 ID、结果可见性，以及用户同时发消息时是否会排队。若桌面版本没有可用接口，先记录已证实的 CLI 边界；用户可以在原会话调用 MCP 读取待办，但这一方式只证明免转贴，需单独标记自动续轮仍待接通。

验收用真实 MCP 服务和真实客户端，单元或模拟测试覆盖故障注入。独立验证至少包括以下场景。[独立评审指南](../reviewing.md)

1. 从派单到结果回投只需一条用户输入，目标会话 ID、工作区、持久化任务记录一致。长于 120 秒的执行仍可回报，长回报正文可完整读取。
2. 目标在线但忙碌、完全退出和审批卡住分别可见，待办可恢复。runner 与 Arena 各重启一次，已持久化的任务、回报和回投队列可查。
3. 模拟客户端开始执行后断连、回报已保存但响应丢失、旧执行结果晚到。对比实际执行轮数、提交数和任务事件，确认只出现一次有效推进。
4. 两个同名会话、过期凭据、已有修改的 worktree 和变动后的合并候选均按设计处理。复审意见及合并结果可对应到准确的提交。

开始实现前按 [工作流程](../../AGENTS.md#3-工作流程) 写阶段工作单，记录实际承接组合、原会话续接的预验证结果及第一阶段范围。
