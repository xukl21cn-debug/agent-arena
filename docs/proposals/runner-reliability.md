# Runner P3：可靠性与恢复

**状态：四步实现完成（`acc5fe7`、`69752ef`、`b34e585`、`9bd89a1`），真实二进制冒烟找出并修掉两个缺陷（`6536d47`），全量测试通过，待评审与用户验收。** 分支：`feat/runner-reliability`。基线：`main` @ `7e33dcf`。

## 1. 背景

P1（最小闭环）、P2（管理与观测）、P2.5（页面派单）已合入。当初的 runner proposal 把「可靠性与恢复」整体留给 P3，验收口径是：**任务执行中杀掉 runner，重启后能恢复或标记待接管；不出现双重提交；超时和失败有明确的事件和回报。**

本文只处理这一件事。多客户端、并发与 worktree 隔离仍属 P4。

## 3. 目标与非目标

### 目标

1. **重启恢复**：runner 在执行中被杀后重启，租约还有效就接着跑完这一轮；已过期就留下证据、转人工。
2. **不丢结果、不重复**：任何一轮的回报最多提交一次，提交不成功就留在本地等补交。
3. **断线重连**：执行中 server 重启，runner 自动重新握手、重新加入工作域并继续。
4. **人工有出口**：「待接管」的任务可以「继续本轮」，不必重建任务。
5. **取消名副其实**：取消后任务是「已取消」，进程被终止，不会误伤别的任务。
6. **看得见**：领取、续跑、完成、超时、失败、取消、提交失败都有事件和带原因的回报。
7. **命令可靠**：队列有界，游标跨 server 重启不会吞命令。

### 非目标

- 多 runner 并发、worktree 隔离、其它客户端适配器（P4）。
- 失败的轮次自动重试：仍进「待复审」并写明原因，由人决定返工还是取消。
- 新增任务状态（类型里预留的 `timeout` 继续不用），不改 `submit_work_result` 的线上格式。
- 注册表持久化（仍是内存里的观测数据）；`/work` 与 `/runners` 互相跳转。

## 4. 方案

### 4.1 重启恢复

本地状态文件里每条 `running` 记录带上 runner 进程的 `instanceId`（每次启动生成）。启动时先做一次恢复扫描，再进入轮询：

- **别的进程留下的 `running` 记录就是孤儿**。逐条用 `get_task` 向服务端核对。
- 任务仍是 `working`、轮次和认领号都对得上：**用原来的认领和原来的 DSH 会话续跑**（`--session-id`），同时恢复租约续期。续跑的提示词在原交接内容前加一句：上次执行途中被中断，工作区可能留有未完成的改动，先看现状再继续。
- 其它情况（租约已过期、已转待接管、已结束）：记录标成 `interrupted`，向注册表发一条警告事件，写明任务、轮次、会话和服务端状态，等人工处理。

本进程自己的 `running` 记录仍按现在的方式跳过。续跑**不回滚**工作区：半成品改动是模型的产出，替用户丢掉比留着更危险；靠会话续跑让它先看现状。

### 4.2 结果不丢

提交之前先把回报写进本地记录（新状态 `submitting`，带回报内容），成功后再标 `submitted`。每次轮询开始和启动时都先把没交出去的补交一遍：

- 服务端回「认领已失效」：说明任务已被取消或转待接管，标 `abandoned`，发一条信息事件附上结果摘要，不再重试。
- 其它错误（连不上等）：留着，下一轮再试。重试次数不设上限，由认领是否有效来决定何时放弃。

服务端对同一认领的重复提交本来就是幂等的，所以补交不会产生第二份回报。本地记录只保留最近 100 条已结束的，未结束的全留。

### 4.3 断线重连

`WorkClient` 加 `reconnect()`：换新传输、重新握手、用原来的名字重新 `join_work`。调用遇到连接类错误或会话失效时触发，然后重试一次。

执行途中 server 重启：续期失败只记日志，重连后接着续；如果宕机期间租约已过期，提交会得到「认领已失效」，走 4.2 的放弃分支。SDK 客户端在会话失效后的具体表现实现时用实验确认，不预设它会自动恢复。

### 4.4 取消

- **runner**：cancel 命令带上任务号时，只有当前任务对得上才终止进程。
- **服务端**：新增 `POST /api/work/tasks/:id/cancel`。以看板用户（协调者）身份强制取消，需要填原因；如果某个 runner 正在跑这个任务，同时给它排一条 cancel 命令去终止进程。
- **工作页**：未结束的任务上有「取消任务」。
- runner 被取消后的提交会得到「认领已失效」，走 4.2 的放弃分支，发一条「任务已取消，结果不再提交」的事件。

`/runners` 页的取消保留，作为不看任务细节时的急停，语义相同。

### 4.5 继续本轮

- **服务端**：`store.resumeRound(taskId)`，只对「待接管」且当前轮还没有执行回报的任务开放——也就是执行途中被打断的情况。复审或合并阶段被打断的不适用，仍走接管或取消。效果是状态回到 `rework_requested`，理由写「已请求继续第 N 轮」。REST 为 `POST /api/work/tasks/:id/resume`。
- **runner**：不需要新逻辑。`rework_requested` 会让它领到一个新的认领，认领号变了就允许再执行，并且沿用该任务之前的 DSH 会话续跑，这一轮此前没有回报，提交不会冲突。
- **工作页**：「待接管」的任务上增加「继续本轮」，和现有的「接管任务」并排。

### 4.6 事件与回报

runner 向注册表发这些事件：领取任务、会话建立、续跑、完成、超时、失败、被取消、提交失败、放弃提交。`wait_for_work` 连续返回 `needs_attention` 时只发一次「有任务待接管，暂停接单」，不每 5 秒刷一条。

超时和失败的回报仍写进 `unresolved`，状态机不变。

### 4.7 命令队列与游标

- **代次**：registry 实例启动时生成一个 `epoch`。轮询时带上它，服务端发现不一致就从 0 开始投递，并在批次里返回新的 `epoch`；runner 把 `{ epoch, seq }` 一起存。
- **有界**：每次轮询时丢掉序号不大于该 runner 游标的命令（这些已经处理过），队列最多保留 100 条。

线上改动：`GET /api/runners/:id/commands` 多一个可选的 `epoch` 参数，`RunnerCommandBatch` 多一个 `epoch` 字段。

## 5. 验收

1. 执行中杀掉 runner，租约过期前重启：同一个 DSH 会话续跑并提交，服务端这一轮只有一份回报。
2. 同上但租约已过期：任务转待接管，`/runners` 有中断事件；工作页点「继续本轮」后 runner 用原会话续跑并提交。
3. 执行中重启 server：runner 自动重连并完成当前轮。
4. 提交时 server 不可达：结果留在本地，恢复后补交，恰好一次。
5. runner 离线期间排队的取消，不会杀掉它重连后在跑的另一个任务；工作页取消后任务为「已取消」，进程被终止。
6. server 重启后旧游标不吞命令；队列长度有上界。
7. 超时、失败、取消都有事件和带原因的回报。
8. `pnpm typecheck`、`pnpm test` 全绿。

## 7. 风险

- **续跑面对的是半成品工作区**。不回滚是有意的取舍，靠提示词让模型先看现状；如果实测发现模型会重复已做过的操作，再考虑在续跑前让 runner 附上 `git status` 的摘要。
- **DSH 会话续接**依赖 `--session-id`，此前调研和 P1 实测都可行，但「进程被杀之后」的会话状态没有专门验过，冒烟时重点看。

### 真实二进制冒烟

单元测试和端到端测试都是绿的时候，用构建出的 `runner/dist` 和 `server/dist` 在临时目录里起了真实进程，走四个场景。它找出了进程内测试看不到的两个缺陷：

| 现象 | 根因 | 处理 |
|---|---|---|
| runner **空闲轮询时**被杀后重启，下一个任务卡在 `working`，新 runner 只得到 `in_progress` | 服务端挂着的 `wait_for_work` 比它的客户端活得久。SDK 的中止信号在连接断开时不触发，等待一直留到自己超时；这期间新建的任务被它领走，认领属于一个已不存在的会话。任务要等满租约（默认 30 分钟）转待接管，再由人工继续 | 请求自带“响应写出前连接就没了”的中止信号，与 SDK 的信号合并。探针实测：杀掉客户端 0.5 秒内等待者消失，新任务保持待领取，活着的 worker 领到了它 |
| runner 日志里出现 `EPERM: operation not permitted, rename …state.json` | 状态文件靠“写临时文件再改名”替换，Windows 上文件被别的进程短暂打开时会拒绝替换（杀毒、索引）。P3 让状态文件的写入频繁了很多，把一直存在的隐患放大了 | 改名被拒时最多重试 1 秒，临时文件名带进程号。用另一个进程占住文件的方式做了确定性的回归测试 |

整改后冒烟 4 个场景 22 项检查全部通过：工作页取消正在执行的任务；执行中杀掉 runner 再重启后续跑，离线期间排队的取消没有误杀它正在跑的任务；DSH 运行中重启 server 后这一轮仍被交上；全程没有状态文件写入失败。

### 实现与方案的出入

- **提交失败时保留 3 次快速重试**。方案写的是交不出去就留到下一轮；实测 server 刚重启时，旧连接上的第一个请求会被重置，当场再试一次就能接上，不必等约 5 秒的下一轮。服务端明确回答的错误仍然立即处理，不重试。
- **回报被服务端连续拒绝 5 次后停止重试并上报**。方案只写了「认领已失效才放弃」；一个始终被拒的结果无限重试没有意义。连不上和身份丢失不计次。
- **看板取消不限于看板派发的任务**。方案写的是「以看板用户身份强制取消」；工作域里看板的接管本来就不受协调者身份限制，取消与之一致。
- **「继续本轮」的轮次也带上被中断的提示**，并且同一轮次的后一个认领继承前一个记录的会话号，这样下一次尝试若在报告会话号之前又被杀，会话仍然找得回。
- **判断会话是否失效用 `instanceof StreamableHTTPError`**。SDK 没有设置 `error.name`，按名字判断永远不命中，这一点是实验中发现的。

### 仍待办

- 用真实 DSH 冒烟一次「执行中杀掉 runner 再重启」。冒烟用的是测试里的假 DSH，验证的是 runner 与服务端之间的全部环节；模型在会话被续接之后的表现需要模型额度才能看。
- 工作页「取消任务」「继续本轮」两个按钮的人工体验。
