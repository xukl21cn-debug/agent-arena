## 2. GLM 违反「不改服务端」，但它是对的

工作单写了「服务端不该再改」。GLM 改了 `room.ts` 的 `syncSeat`，并主动说明。

**我验证了这个 bug 在 main 上真实存在**：

```text
REST 开围棋局（agentColor: white）→ status: playing, game: go
agent 调 join_game(seat: white)
→ isError: true
→ {"code":"INTERNAL_ERROR","message":"This room is not running gomoku."}
```

**这是 P3b-3 的真实缺陷，而且很严重**：网页开围棋局后，AI 根本连不进来。
M4 的核心流程（网页先开局 → agent 加入）100% 走不通。

修复后：

```text
join isError: false
→ {"participantId":"p_b41712","seat":"white","phase":"playing",
   "state":{"game":"go",...}}
```

`state.game` 仍是 `go`，`seats` 正确镜像。**修复有效，而且没有把围棋误判成五子棋。**

### 为什么之前测试没发现

GLM 说得对：所有既有测试都是**先 join 再开围棋局**。而真实流程是
**先开局再 join**。这个顺序差异是关键。

**这是一次好的「越界」**：工作单的边界是为了防止范围蔓延，不是禁止修 bug。
GLM 把修复单独成一个 commit 便于审查，处理得当。

## 4. `scorePreview` 客户端镜像：我做了等价性验证

`GoState` 上没有 `scorePreview`（那字段只在 MCP 的 `GoAgentStateView`），
服务端又冻结，所以 GLM 在 `web/src/scoring.ts` 镜像了一份引擎算法。

**复制算法有漂移风险**，所以我做了对照：

```text
280 个随机 9×9 局面（7 个种子 × 40 次）
每个局面随机标 15% 的死子
逐字段比较 blackArea / whiteArea / komi / blackTotal / whiteTotal / winner / margin
→ MIRROR MATCHES ENGINE on every field
```

**镜像与引擎完全等价。** 而且：

- 注释明确写了「引擎为准，不一致即此镜像是 bug」
- 终局分数始终读权威的 `state.score`
- GLM 的 e2e 脚本里有独立复算交叉验证

这个处理方式是对的：**预览可以近似，终局必须权威**。

## 5. 大厅保留直接开局按钮

GLM 的说明：

> ready 流开局固定是五子棋（服务端冻结），若 lobby 只剩准备按钮，
> 新房间永远开不出围棋。

我核对了 `Controls.tsx`：游戏选择 + 直接开局按钮在所有阶段可见，
准备按钮仍是 lobby 的主路径。

**这个判断是对的**：如果只留准备按钮，围棋就开不出来了。
服务端冻结的前提下，这是唯一可行解。

**遗留**：等 P1c 的 ready 流支持 `game` 参数后，可以统一成
「准备 + 游戏选择」，去掉直接开局按钮。记入待办。

## 6. 一个既有问题（不是 P3b-4 引入）

测试中发现：人类开围棋局、AI 没接入时，白方永远不动，人类**不能 pass**
（`NOT_YOUR_TURN`）。

但**可以认输**（带 `actor: 'human'` 返回 200 → `finished`）。

所以不是完全卡死，只是「不能替对手走棋」——这是**正确**的。
五子棋同样如此。

不过体验上有个小缺口：**AI 没接入时，用户只能认输，不能等**。
工作单里 P1c 的「60 秒提示」覆盖了提示，但没有「AI 掉线后自动判负/暂停」的机制。
这个留给后续（P1c 的 `paused` 状态，当时刻意没做）。

## 7. 我测试脚本的三次误报（记录）

教训升级：**测试一个双人系统时，必须确保双方都在场**。
后来加了真实 MCP agent 作为白方，全部通过。
